## Entorno / Dev Container

- [2026-08-30] Cuando necesites administrar la BD o phpMyAdmin **dentro** del dev container, no uses docker: el daemon no puede arrancar (el seccomp bloquea _user namespaces_ y no hay `CAP_SYS_ADMIN`). Corre phpMyAdmin con `php -S 0.0.0.0:8080 -t /usr/share/phpmyadmin` apuntando a `db:3306` (root / root_password), o levanta `db`/`pma` desde el host con `docker compose up -d`.
- [2026-08-31] Si phpMyAdmin no responde en `:8080` dentro del dev container, verifica que la imagen tenga `php-cli`/`php-mysql`/`phpmyadmin` y que node pueda leer `/etc/phpmyadmin/config-db.php` y `/var/lib/phpmyadmin/blowfish_secret.inc.php` (son `640 root:www-data` por defecto y bloquean el login) y que `$dbserver='db'`. La instalación ya está en el `Dockerfile` y el arranque en `postStartCommand` de `devcontainer.json`, pero requiere `docker compose build app` en el host.

- [2026-08-31] La BD host tiene `max_connections=151` (básica) y cada proceso Node (next dev + cada `npx tsx`/subagente) abre su propio pool de hasta 10 conexiones; con varios procesos/scripts simultáneos se satura con `ER_CON_COUNT_ERROR (1040) "Too many connections"` y ni siquiera el cliente mysql puede conectar. Para liberarlas, conecta como root (`mysql -hdb -uroot -proot_password`) y mata las conexiones colgadas del usuario: `SELECT id FROM information_schema.processlist WHERE user='jotron' AND id<>CONNECTION_ID()` en bucle con `KILL <id>`. Minimiza los scripts `tsx` concurrentes y cierra siempre con `process.exit(0)`. Además, al fumar-probar con `next dev` evita lanzar muchos `curl` en paralelo contra rutas sin compilar: la tormenta de compilación + los pools (con `keepAlive`) agotan las 151 y producen errores 500 falsos (p. ej. en la ficha del vino); matar `next dev` libera las conexiones al instante, y las peticiones secuenciales (una cada ~1s) no saturan.

## Flujo de BD

- [2026-08-30] Cuando cambies el schema (`src/db/schema.ts`), sigue el flujo Drizzle en orden: `pnpm db:generate` → `pnpm db:migrate` (en dev puedes usar `pnpm db:push`). Tras tocar el seed, corre `pnpm db:seed`.
- [2026-08-31] Con drizzle-kit 0.31, el script `pnpm db:generate` (emite `generate:mysql`, deprecado) no genera ninguna migración y `pnpm db:push` falla al "pulling schema" en esta BD: usa `npx drizzle-kit generate` → `pnpm db:migrate`, que sí funcionó y creó `0001_loving_gladiator.sql`.
- [2026-08-31] Para correr `db:migrate`/`db:seed` o conectarte a la BD dentro del dev container, el `DATABASE_URL` debe apuntar a `db:3306` y no a `localhost:3306` (el localhost no está expuesto; `local -> ECONNREFUSED`). El `.env`/`.env.local` venían con `localhost`.
- [2026-08-31] El seed de `src/db/seed.ts` salta ("already seeded") si existe cualquier `users`, así que para repoblar con un nuevo dominio hay que vaciar la BD antes: `SET FOREIGN_KEY_CHECKS=0` + `TRUNCATE` de todas las tablas (salvo `__drizzle_migrations`) y luego `pnpm db:seed`.
- [2026-08-31] No confíes en que `db:migrate` "pasa" = schema aplicado: la tabla `__drizzle_migrations` tenía registrados los hashes de 0002/0003/0004 pero el SQL no se había aplicado (faltaban `wine_id` en `cart_items`/`order_items` y el seed falló con `Unknown column 'wine_id'`). Cuando el seed falle en una columna, verifica la existencia real de columnas/tablas con `SHOW COLUMNS`/`SHOW TABLES` y aplica a mano el SQL de la migración pendiente (ALTER AÑADE columna/índice/FK) en lugar de re-generar migraciones.
- [2026-09-01] Las migraciones Drizzle 0000-0009 NO son replayables desde un estado vacío: son parches incrementales que chocan al aplicarlas de cero (p. ej. 0003 falla con "Duplicate column wine_id" en `cart_items` y 0007 con "Identifier too long" en una FK). `drizzle-kit migrate` falla en silencio sobre BD vacía. Para reconstruir el schema tras vaciarlo, aplica los `.sql` 0000-0009 con el cliente mysql (los CREATE TABLE construyen todo el esquema; los ALTER conflictivos son redundantes/repetibles) y registra los hashes sha256 en `__drizzle_migrations` a mano para que el journal quede consistente.
- [2026-09-01] El seed (`src/db/seed.ts`) solo se ejecuta sobre BD vacía y su cleanup está incompleto para reseed: falta borrar `orders`/`order_items`/`order_events`/`invoices`/`carts`/`cart_items` y `wines` más sus pivotes (`wine_wineries`/`wine_grapes`/`wine_categories`/`wine_guarantees_of_origin`/preferencias/favoritos) en el orden correcto, y los ids de seed (p. ej. `statusId:1`, `shippingTypeId:1`) asumen que el AUTO_INCREMENT empieza en 1 (se rompe al reseed porque el contador no se resetea). Para reseed: vacía toda la BD (drop tablas), reaplica el schema y corre el seed; si necesitas forzar sobre datos existentes, añade un flag `FORCE_SEED` al guard de idempotencia y completa el cleanup de tablas hijo antes que sus padres.
- [2026-09-01] No uses `ilike` de drizzle-orm en este proyecto: la BD es MariaDB/MySQL y `ilike` emite el operador SQL `ILIKE` (sintaxis PostgreSQL) → `ER_PARSE_ERROR` cada vez que un usuario filtra por texto (búsqueda en `/productos`, endpoint admin). Usa `like` (la collation de las columnas es `utf8mb4_uca1400_ai_ci`, así que ya es case- y accent-insensitive, mismo comportamiento que `ilike` en texto).

- [2026-10-03] Las migraciones ya se versionan desde `drizzle/migrations/0000_baseline.sql` (antes `drizzle/migrations/` estaba en `.gitignore` y un clon limpio no tenía migraciones: fallaba el `COPY` del `Dockerfile` y el entrypoint de dev). Si una FK de Drizzle genera un nombre de más de 64 caracteres, MySQL da `ER_TOO_LONG_IDENT` y `drizzle-kit migrate` sale con código 1 sin mostrar el error: define la FK con `foreignKey({ name: '<corto>', ... })` (patrón de `ugop_guarantee_id_fk`). Para ver el error real, ejecuta `migrate()` de `drizzle-orm/mysql2/migrator` desde un script.

## Arquitectura

- [2026-09-19] Cuando una constante/URL debe usarse desde cliente (`'use client'`), tests y scripts Node a la vez, no la definas ni en un componente cliente ni en un módulo con `import 'server-only'`: ponla en un módulo neutro como `src/lib/constants/images.ts` e impórtala desde los tres lugares (ocurrió con `PLACEHOLDER_IMAGE_URL`, inicialmente duplicada y centralizada después). Los scripts `tsx` de `scripts/` tampoco pueden importar un módulo `server-only`: si el script necesita Cloudinary (p. ej. `migrate-images-to-cloudinary.ts`), configura el SDK (`cloudinaryV2.config({ url: CLOUDINARY_URL })`) dentro del propio script en vez de reutilizar `src/lib/cloudinary.ts` — al ejecutarlo con tsx, `server-only/index.js` lanza "This module cannot be imported from a Client Component module".
- [2026-08-31] La tabla `categories` es compartida entre el dominio heredado de `products` (21 categorías: Electrónica, Ropa…) y el nuevo dominio de vinos (6: Tinto, Blanco, Rosado, Dulce, Generoso, Pasas); no hay columna de dominio que las distinga. Para que el panel admin de vino no muestre el ruido genérico, filtra por las categorías referenciadas en `wine_categories` (inner join distintivo), no devuelvas todas; el caso borde es que una categoría recién creada no aparece hasta vincularse a un vino (tradeoff aceptado).
- [2026-08-31] El middleware (`src/middleware.ts`) con NextAuth considera "protegidas" todas las rutas que no estén en su allowlist, así que las páginas estáticas públicas de FR-11 (slug de un solo segmento: `/nosotros`, `/privacidad`, `/aviso-legal`…) salían redirigidas a `/auth/signin?callbackUrl=...` (307). Si necesitas una ruta pública nueva de un solo segmento, añádela como pública en `authorized` (patrón probado: rutas `/^\/[^/]+$/` públicas salvo `['/cuenta','/checkout','/admin','/auth','/pedido']`), porque el matcher solo excluye `api/` y `_next/*` del control de sesión.
- [2026-09-01] Dentro de una `db.transaction` de Drizzle sobre MySQL, una lectura inmediata tras `insert`/`delete` en la misma transacción puede devolver datos obsoletos (InnoDB `REPEATABLE READ` lee un snapshot previo). No relas `getX()` para construir la respuesta del PUT/POST dentro de la transacción: devuelve los arrays/campos que acabas de escribir. (Ocurrió en `setUserPreferences`: el PUT devolvía arrays vacíos/parciales aunque la BD quedaba correcta.)
- [2026-09-01] En F6 existían dos árboles de login que colisionaban en la misma URL `/signin`: la ruta real bajo `src/app/auth/signin/` y una copia muerta bajo el route group `src/app/(auth)/signin/` (este además importaba un `SignInForm` con `useToast` muerto). Para rutas públicas de un segmento coincidentes, verifica qué árbol referencian realmente los componentes/Header y elimina el duplicado; `rm -rf src/app/(auth)` y quedó solo `/auth/signin`.
- [2026-09-20] Cuando añadas una ruta pública nueva de **dos segmentos** (`/bodegas/[id]`, `/categoria/[slug]`) o un listado nuevo alcance largamente desde la raíz, añade su rama a `isPublicPath` de `src/middleware.ts`, aunque su primer segmento ya coincida con una ruta ya pública: el middleware solo marcaría el padre, no los hijos, y la página quedaría exigiendo login (templates con `/^\/[^/]+\/[^/]+$/` no están en la allowlist). Verificado: sin editar el array, `/categoria/tinto` y `/bodegas/1` redirigían a login; tras añadir `startsWith('/bodegas')`/`startsWith('/categoria')`, smoke curl → 200.
- [2026-09-20] En `src/lib/db/queries.ts`, **no importes `leftJoin` desde 'drizzle-orm'**: la versión del repo no lo exporta (`TS2305: has no exported member 'leftJoin'`). El join relacional ya se usa como método del query builder (`.leftJoin(...)`) sin importarlo; déjalo fuera de la lista de imports al editar ese fichero.
- [2026-09-20] Cuando hagas un `update` de Drizzle sobre MySQL en `queries.ts`, no uses `.$returningId()`: solo existe sobre INSERT (`TS2339` en `MySqlUpdateBase`); devuelve el `{ id }` desde los argumentos (ocurrió en `markContactMessageRead`).
- [2026-09-20] Cuando insertes un bloque nuevo en `src/lib/db/queries.ts` anclado a `return { data: items, meta: {...} }`, usa el JSDoc de la siguiente función como contexto único del match: ese return se repite idéntico en varias queries admin y el primer match rompió la función contenedora (`getOrdersByUser` quedó con `TS2304: items`).
